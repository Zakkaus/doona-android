# doona-core contract fixtures

Example payloads for `plans/v1/core-api.md` (schema 2), parsed by the Rust tests in `crates/doona-core` and by a Kotlin JVM test of `vpn/CoreDto.kt`. Change them together with both sides. The two `hk-01` nodes are distinct endpoints with the same display name, and the second one's probe failed with `local_network`; the running snapshot carries the `local_network` warning, and the stopped one kept no yesterday (`yesterdayByNow` null); the subscription URL's token is a placeholder. The stats replies use one invented day, 2026-11-22: a five-second rate window, today and yesterday by the hour with each outbound's payload, the daily totals (2026-11-20 had no bytes, so it is absent), and two nodes' details with their latency tests, one of them failed.

The rule mode payloads are what the core produces for its template `cn-direct` version 2: the catalog's `mainGroupId` and `ruleSource`, the five rows of `rules` with their real ids and `rulesRevision`, `setRuleSource` and `setMode` arguments, and `effectiveConfig` over one subscription with two nodes (`hk-01`, `jp-01`), whose text names each node only by its code, `n-` and the first 8 hex digits of its id. Today's `byRule` in the usage reply uses the real ids of the `GEOIP,CN` and `MATCH` rows, so its bytes add up to the `direct` and `g-Proxy` outbounds. Regenerate the ids from the core's tests when the template changes; never write them by hand.
